## Key decisions made

- **`parent_id` mapped as a plain `UUID` column, not `@ManyToOne`** — the
  domain references the parent by `CategoryId` (aggregates reference each
  other by identity), `fromDomain` stays a pure function (no parent-entity
  resolution), and no code navigates the hierarchy through the ORM (the
  ancestor walk is a native CTE, tree building is in-memory). The DB FK keeps
  referential integrity without JPA knowing about it.
- **No Jakarta Bean Validation annotations on JPA entities** — entities are
  only built via `fromDomain` from an already-validated aggregate, so entity
  annotations would be a third copy of invariants (after the domain and the
  DDL CHECKs) that can only fire on a domain bug, and would fail at flush
  time far from the use case. Bean Validation stays at the untrusted boundary
  (`@Valid` on web DTOs). Revisit only if an entity ever gains a write path
  that bypasses the domain.

## Concepts explained / learned

- **`@Version` drives more than optimistic locking**: Spring Data uses a null
  version to route a new entity to `persist()` instead of `merge()`; without
  the annotation, application-side ids force a useless SELECT before every
  INSERT.
- **Detached-entity `save()` cost**: `fromDomain` builds a detached entity, so
  updates go through `merge()` — a SELECT to reload managed state before the
  UPDATE. Structural price of the "domain aggregate ↔ throwaway entity"
  pattern, already paid by `account`, acceptable at this scale.
- **`equals()` on entities**: two transient entities (null id) must not be
  equal; `instanceof` survives Hibernate proxies where `getClass()`
  comparison breaks.
- **Validation layering**: DTO (`@Valid`, untrusted input) → domain
  (invariants, source of truth) → DDL (defense in depth, covers out-of-band
  writes). Entity-level Bean Validation adds no coverage between the last two.
